# ADR-0012: i18next + react-i18next + expo-localization

Status: Accepted · Date: 2026-11-23 · Implemented on `feat/monorepo-starter`

Source: [decision record](../00-product/monorepo-starter-decisions.md) Q26.

## Context

Options: a full i18n setup from day one; centralised string files with i18n added later; inline
strings (costly to retrofit). Client projects often need a second language eventually.

## Decision

- i18next + react-i18next, with `expo-localization` for device language.
- English only in the starter.
- Each feature owns a namespace (`packages/features/src/<feature>/locales/en.json`); shared UI
  strings live in `packages/ui`.
- Typed keys; user language override persisted through redux-persist.
- The `/design` Copy table is the source for keys.
- Right-to-left layout is out of scope.

## Consequences

- Every user-facing string goes through `t()` from day one.
- Adding a language is adding JSON files.
- Tests need the i18n provider in `renderWithProviders`.

## Implementation notes (2026-11-23)

- Implemented as decided with an i18next instance (`createInstance`, `initAsync: false`) so the first render is translated. Language override is a persisted preference.
